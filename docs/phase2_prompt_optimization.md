# MODULE_DETECTION_PROMPT 提示词优化方案

> **目标**：针对 Phase 2 VLM 组件识别提示词进行系统化分析和优化
> **当前模型**：qwen3.6-plus（DashScope API）
> **测试图片**：1024×1024 像素正交正视图
> **原则**：只改提示词文本，不改代码逻辑

---

## 二、逐项分析与优化建议

### P0-1: 3m×3m 网格规则与 VLM 能力不匹配

**现状**：
- 提示词要求"按 3m×3m 网格分割墙面（每格约图片宽度的 1/4~1/6）"
- 实际输出：4 个 facade 组件，bbox 范围从 250×200 到 300×300 像素
- 问题：VLM 无法精确理解"3m"对应多少像素，"1/4~1/6"的换算也容易出错
- 更严重的是：不同楼层/位置的墙面可能需要不同的网格尺寸

**实际输出验证**（manifest.json）：
| 组件 | bbox | 像素尺寸 | 宽高比 |
|------|------|----------|--------|
| facade_panel_center_upper | [350,150,650,450] | 300×300 | 1:1 |
| facade_panel_left_upper | [50,450,300,650] | 250×200 | 1.25:1 |
| facade_panel_right_upper | [700,450,950,650] | 250×200 | 1.25:1 |
| facade_panel_center_lower | [350,650,650,850] | 300×200 | 1.5:1 |

→ 宽高比从 1:1 到 1.5:1 不等，说明 VLM 并没有真正遵循"3m×3m"规则

**优化方案**：
- 删除"3m×3m"这个对 VLM 来说不可操作的概念
- 改用 **"按窗间墙自然分段"**：墙面面板的边界由窗户/门等装饰组件的位置决定
- 明确给出像素参考范围："面板宽度约 200-350px（图片宽度 1024px 时）"
- 允许不同楼层有不同尺寸的墙面面板

---

### P0-5: "同种窗户只识别1个"与 reusable_groups 需求矛盾

**现状**：
- 提示词写道："相邻外观相同的窗户 → 只识别1个代表"
- 但实际输出：识别了 9 个 window 组件（comp_009~comp_019）
- 代码中 `build_reusable_groups()` 需要所有实例来计算 `all_instances`、`size_range`
- Phase 3 的 `deduplicate_components_by_reusable_type()` 是代码层去重，不需要提示词层去重

**矛盾分析**：
```
提示词要求："只识别1个代表" → VLM 返回少量实例
代码需求：所有实例 → reusable_groups.count 正确 → Phase3 去重有数据
实际结果：VLM 忽略了"只识别1个"，返回了全部 → 恰好满足代码需求
```

**优化方案**：
- **删除**"同种窗户只识别1个"这条规则
- 改为：**"每个独立的组件实例都必须单独识别，即使外观相同"**
- 在提示词中明确："去重由下游代码处理，你需要识别出每一个实例"
- 这样既消除了规则冲突，又让 VLM 不再纠结"是否应该省略"

---

### P0-7: 未提供图片尺寸信息

**现状**：
- 提示词中没有任何关于图片尺寸的提示
- VLM 需要输出像素坐标 bbox，但不知道图片多大
- 示例中用了"1000x1000像素"这个假设值，可能与实际不符

**优化方案**：
- 在提示词开头注入动态信息："本图片尺寸为 {width}×{height} 像素"
- 在代码中拼接提示词时插入此信息
- 这样 VLM 就有了精确的坐标参考系

---

### P1-3: type 列表不完整

**现状**：
- 提示词列出的标准类型：`facade, window, door, balcony, roof, roof_slope, base, chimney, decoration, parapet`
- 代码中 `classify_component_subtype()` 还处理了 `steps` 和 `canopy`
- 实际输出中出现了 `window_shop`（商店橱窗），不属于任何标准类型

**优化方案**：
- 补充类型列表：增加 `steps, canopy, shopfront, parapet, dormer`
- 对 `decoration` 增加子类型说明，避免所有装饰都归为同一类

---

### P1-8: Phase 1 语义信息未注入

**现状**：
- Phase 1 输出了丰富的建筑语义：`total_floors=3, building_style=Fairy-tale Cottage, ground_floor=shop fronts, roof.type=hip`
- Phase 2 提示词完全没有利用这些信息
- 导致 VLM 需要从零开始判断建筑结构

**实际影响**：
- Phase 1 说 3 层，但提示词没有告诉 VLM → VLM 可能误判楼层
- Phase 1 说底层是商铺 → 提示词没有提示 VLM 关注商店橱窗
- Phase 1 说 roof type 是 hip → 提示词没有提示 VLM 关注屋顶类型

**优化方案**：
- 在提示词中注入 Phase 1 关键信息：
  ```
  【建筑背景信息】
  - 建筑风格：Fairy-tale Cottage
  - 总楼层数：3
  - 屋顶类型：hip（四坡屋顶）
  - 底层特征：shop fronts with striped awnings
  - 外墙材质：mixed（beige stucco + brown wood）
  ```

---

### P1-9: roof_slope 坡度角判断无操作标准

**现状**：
- 提示词要求"按坡度角分组（30°/45°/60°）"
- 分类标准："缓坡(30°~35°)、中坡(40°~50°)、陡坡(55°~70°)"
- 但 VLM 如何判断角度？没有给出操作方法

**优化方案**：
- 提供视觉判断法：
  - 陡坡（55°~70°）：屋顶斜面高度接近宽度 → 看起来很陡
  - 中坡（40°~50°）：屋顶斜面高度约为宽度的一半
  - 缓坡（30°~35°）：屋顶斜面很平缓
- 简化为 3 个离散类别，不要让 VLM 输出精确角度
- 或者更好的方案：**不要求 VLM 估算角度**，改为"按屋顶视觉形态分组"

---

### P1-11: decoration 类型太笼统

**现状**：
- 所有装饰元素都被标记为 `decoration`
- 实际输出中 decoration 包含了：尖顶装饰(spire)、铁艺栏杆(railing)、壁灯(lamp)、植物(plant)
- 代码 `classify_component_subtype()` 对 decoration 没有子分类
- Phase 3 去重时这些完全不同的东西被归为一组

**实际后果**（manifest.json）：
| 类型 | 实例数 | 包含内容 |
|------|--------|----------|
| decoration | 11 | 3个尖顶 + 1个栏杆 + 4个壁灯 + 2个植物 + 1个攀爬植物 |

→ 11 个完全不同的装饰被分到同一组，Phase 3 只取 1 个代表

**优化方案**：
- 在提示词中将 decoration 拆分为子类型：
  - `decoration_spire`（尖顶装饰）
  - `decoration_railing`（栏杆/栏板）
  - `decoration_lamp`（壁灯/灯具）
  - `decoration_plant`（植物装饰）
  - `decoration_molding`（线脚/装饰条）
  - `decoration_other`（其他装饰）
- 或者在 type 字段中直接用这些细分类型

---

### P1-12: chinese_description 对 Phase 3 生成约束不足

**现状**：
- 格式规范：`[形状] + [比例] + [材质/风格] + [装饰特征]`
- Phase 3 直接用 chinese_description 作为生成 prompt
- 当前输出示例：
  - "标准化墙面面板，宽高比1:1.5，浅色灰泥材质，哥特式拱形装饰"
  - "中型哥特式尖拱窗，木质窗框，双扇设计，带窗台"

**问题**：
- 缺少**视角信息**（Phase 3 要求45°正交视角，但描述只有正面信息）
- 缺少**颜色信息**（Phase 1 识别出了 beige/brown/green，但描述中没有）
- 缺少**尺寸信息**（只有宽高比，没有绝对尺寸参考）
- "标准化墙面面板"这种描述对图像生成模型没有意义

**优化方案**：
- 修改 chinese_description 规范为：
  ```
  [组件类型] + [视觉特征] + [颜色] + [材质] + [尺寸参考] + [装饰细节]
  ```
- 好例子：`"哥特式尖拱窗，粉色木质窗框，带圆形玻璃窗，石质窗台，约80×170px，双扇设计"`
- Phase 3 生成时需要的是"这个东西看起来是什么样的"，而不是"这个组件的工程分类"

## 四、优化后完整提示词

```

═══════════════════════════════════════════
【图片信息】
- 图片尺寸：{width}×{height} 像素
- 建筑风格：{building_style}
- 总楼层数：{total_floors}
- 屋顶类型：{roof_type}
- 底层特征：{ground_floor}
- 外墙材质：{facade_material}，主色{facade_color}
═══════════════════════════════════════════

═══════════════════════════════════════════
【核心规则】
1. 每个独立组件实例都必须单独识别，外观相同的组件也要逐个列出（去重由下游代码处理）
2. 组件边界必须紧贴视觉边缘，bbox 不多不少

4. 禁止将整层墙面作为单个 facade

  - 面板宽度参考：200~350px（1024px宽图片），高度与楼层高一致
  - 面板必须包含窗框之间的空白区域
  - 如果墙面有砖缝/灰缝纹理，面板边界贴合纹理走向
  - 不同楼层的面板尺寸可以不同

装饰类：decoration_spire, decoration_railing, decoration_lamp, decoration_plant, decoration_molding, decoration_other

═══════════════════════════════════════════
【BBOX 坐标规则 - 必须严格遵守】
1. 格式：[x1, y1, x2, y2]，单位是整数像素值
2. x1 < x2, y1 < y2
3. 坐标紧贴组件视觉边缘
4. 所有坐标在图片范围内（0 ≤ x < {width}, 0 ≤ y < {height}）
5. 禁止小数，只输出整数

═══════════════════════════════════════════
【chinese_description 规范】
格式：[组件类型] + [视觉特征] + [颜色] + [材质] + [约略尺寸] + [装饰细节]

好例子：

所有字段缺一不可：
```

## 六、待讨论事项

以下是需要进一步确认的决策点：

1. **Phase 1 信息注入的粒度**：注入多少 Phase 1 信息算合适？全部注入会显著增加 token，是否只注入与组件识别强相关的字段（楼层数、屋顶类型、底层特征、外墙材质）？

2. **decoration 子类型的实现方式**：
   - 方案A：在 type 字段直接用 `decoration_spire` 等子类型 → 需改代码中的类型判断
   - 方案B：type 仍用 `decoration`，在 name 中体现子类型 → 代码改动小但去重不精确
   - 方案C：增加 `subtype` 字段 → 改 JSON schema

3. **facade 拆分策略**：
   - 方案A：按窗间墙自然分段（推荐） → VLM 自主决定面板边界
   - 方案B：保留网格但改为像素参考 → VLM 仍需换算
   - 方案C：两次识别——先识别窗户位置，再算出窗间墙 → 需要两次 API 调用

4. **图片尺寸注入方式**：
   - 方案A：在提示词文本中硬编码（需要代码拼接）
   - 方案B：单独添加一条 user message（多轮对话格式）
   - 方案C：在 system message 中说明

5. **chinese_description 的定位**：
   - 当前它同时服务"组件描述"和"Phase3 生成 prompt"两个用途
   - 是否需要拆分为两个字段？`description`（工程描述）+ `generation_prompt`（生成描述）
